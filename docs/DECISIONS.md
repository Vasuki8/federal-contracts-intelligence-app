## M0 — Project setup

### 2026-10-06 · Python project lives at the repo root
One `pyproject.toml` + `uv.lock` at the root; the importable package is `pipeline/` (tests in `pipeline/tests/`).
**Why:** the commands in CLAUDE.md (`uv run app …`, `uv run alembic …`, `uv run pytest`) run from the root. A uv workspace would add a layer with no benefit while there is one Python package.

### 2026-10-06 · Two Python dependencies beyond the stated stack
- `pydantic-settings`: typed loading of env vars and `.env`; keys are `SecretStr` so they never print in logs or reprs.
- `sqlalchemy`: Alembic requires it. It is used only as Alembic's connection layer, not as an ORM.

`httpx`, `polars` and `pyyaml` are deferred to M1, when code first uses them.

### 2026-10-06 · Alembic: hand-written migrations, sequential IDs, URL from env
- `target_metadata = None`: there are no ORM models, so every migration is written by hand with `op.*` / SQL.
- Revision IDs are sequential (`0001`, `0002`, …): `uv run alembic revision --rev-id 0002 -m "…"`.
- The DB URL comes from `DATABASE_URL` (`migrations/env.py`), never from `alembic.ini`, so no credentials live in the repo.

### 2026-10-06 · Separate test database (`TEST_DATABASE_URL`)
Added `TEST_DATABASE_URL` (not in the BUILD_PLAN env list). Docker creates `fci_test` on first start (`docker/postgres/init/01-test-db.sql`); CI runs the same script.
**Why:** later milestones' tests will create and truncate tables; they must never touch local dev data. As a guard, the test fixture refuses any database whose name doesn't end in `_test`. DB tests **fail** rather than skip when the database is down, so a missing DB can't hide a broken test run.

### 2026-10-06 · One `.env` at the repo root, shared by both packages
- Pipeline: `pydantic-settings` reads `<repo>/.env`.
- Web: `next.config.ts` loads `../.env` with Node's built-in `process.loadEnvFile`; `kysely-codegen` runs under `node --env-file-if-exists=../.env`.

Variables already set in the environment (as in CI) take precedence; a missing `.env` is fine. No `dotenv` dependency is needed.

### 2026-10-06 · TypeScript pinned to 6.0.x, not 7.x
`typescript-eslint` 8.x (pulled in by `eslint-config-next`) declares `typescript >=4.8.4 <6.1.0`. Revisit when it supports TS 7.

### 2026-10-06 · ESLint pinned to 9.x, not 10.x
Tested: with ESLint 10.12, `eslint-plugin-react` 7.37.5 (from `eslint-config-next` 16.3.8) crashes with `contextOrFilename.getFilename is not a function`. The react, jsx-a11y and import plugins all declare `eslint <= 9`. npm marks ESLint 9 deprecated, but it works. Revisit when `eslint-config-next`'s plugins support 10.

### 2026-10-06 · Other web dependencies beyond the stated stack
- `pg`: Kysely's Postgres driver; `kysely-codegen` needs it too.
- `@tailwindcss/postcss`: Tailwind v4's integration with Next.js.
- `vite`: Vitest 5 requires it as a peer dependency.

pnpm 10 blocks dependency build scripts by default; only `unrs-resolver` (native resolver used by ESLint's import plugin) is allowed.

### 2026-10-06 · Kysely: snake_case, committed generated types, CI drift check
- Columns stay snake_case in TypeScript (no `CamelCasePlugin`), so TS and SQL read the same.
- `web/src/db/types.ts` is generated by `pnpm db:codegen` and committed, so the web app type-checks and builds without a database.
- The CI job `db-types` migrates a fresh DB and runs `kysely-codegen --verify`; it fails if a migration was added without regenerating types.
- `alembic_version` is kept in the generated types (the M0 plan said it would be excluded). `/api/health` reads it to report the schema version, and it gives the web tests a real table to type-check against.

### 2026-10-06 · Docker image `postgres:16` (Debian), not `-alpine`
Alpine uses musl, whose locale and collation behavior differs from the glibc/ICU builds used by Neon and Supabase. Sorting text should behave the same locally and in production.

### 2026-10-06 · Node 22 and pinned CI tool versions
- `.nvmrc` = 22. Vitest 5 needs Node `^22.12 || ^24`, and 22 matches the dev container.
- CI pins `astral-sh/setup-uv@v10.2.0` exactly, because that action no longer publishes floating major tags (the latest floating tag is v7). It also pins uv `0.12.23`; the lockfile was created with uv 0.11.32 and verified unchanged under 0.12.23 (`uv lock --check`).

### 2026-10-06 · Official data-source docs not reachable from the build environment
The build container's network policy blocks `open.gsa.gov`, `api.sam.gov`, `sam.gov`, `api.usaspending.gov` and `files.usaspending.gov`. `docs/data-sources.md` is therefore an **unverified skeleton**. M1 must fill it from the official docs, and save real fixtures, before any client is written. M0 doesn't use any API, so there is no docs-vs-plan conflict to record yet.
